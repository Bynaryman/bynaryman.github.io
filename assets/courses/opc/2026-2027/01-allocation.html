Dynamic memory allocation on the heap

We open an image and discover its dimensions. Where do we store its pixels?

  1. Make an independent copy.
  2. Store values and find memory errors.
  3. Organise arrays, strings and matrices.
  4. Group data with user-defined types.

Say: “An image editor opens a file, discovers its dimensions and needs storage for its pixels. It may also need a separate copy to edit while preserving the original. Today we learn how to request that storage on the heap, use it correctly and release it.” This motivates allocation without claiming that malloc is the only way to use a runtime size. We are not implementing an image decoder: use a tiny string to make copying visible, integers to learn byte counts and initialisation, then matrices to organise rows and columns. Structures group related data; retain the source course’s address example. Keep Vim and a terminal beside Firefox. Ask for a prediction, edit/run C, inspect the result, then explain with the slide. There are no per-section time targets.

2. Arrays and memory errors

We copied existing characters. Now we create an array of values.

How many bytes? What values are there before we write?

Say: “strcpy filled our allocation with existing characters. What if we need fresh storage for numbers, such as a row of pixel intensities? malloc gives us bytes, but we must calculate how many and write the values ourselves.” The next integer program uses zero values so the later memory faults are easy to isolate. This is a simple numeric model; image formats need not store pixels as C int values.

How much space for integers?

We need space for 100 values, initially set to zero.

int *p = malloc(count * sizeof(int));
if (p == NULL) {
    fputs("Allocation failed\n", stderr);
    return EXIT_FAILURE;
}

Count elements, request bytes

void *malloc(size_t size);   // From <stdlib.h>

  • sizeof is an operator giving a size in bytes.
  • sizeof(int) is the size of one int, not the pointer.

Sizes depend on the platform. In C, the void * result needs no cast.

Make the new point explicit: malloc takes bytes, whatever the element type. The string needed one byte per char; the numeric array needs sizeof(int) bytes per int. strcpy performed the writes in the opening; here our loop performs them. Inspect count * sizeof(int) in the program just run. sizeof is an operator, not a function. size_t is unsigned and can represent at least 0 through 65535. No cast of malloc is required in C. For unrestricted external counts, check multiplication overflow before allocation.

Where does the program keep its data?

Illustrative 16-bit address space; real address widths and layouts vary.

After running the integer example, locate count and the pointer p in the active stack frame, and the allocated integers on the heap. Dangling pointer

A pointer to an object whose lifetime has ended.

free(p) releases the block; it does not set p to NULL.

Repair: finish reading before releasing the block.

printf("first=%d, last=%d\n", p[0], p[count - 1]);
free(p);

Distinguish the dangling pointer (state after the object’s lifetime ends) from the invalid read (using it to access that object). free does not remove the pointer variable or set it to NULL; the storage can be reused. The drawing is a lifetime model, not a claim about preserved byte values or a valid pointer value after free. Ask where free should go, then reveal the repair and edit it in Vim. Run make valgrind FILE=05-integers.c with input 4 and read zero errors. Do not suggest setting p to NULL makes a subsequent read legal. Any other aliases would still be dangling. A second free is invalid too. Bridge: “We fixed when we call free. Now suppose array creation moves into a helper function: can returning an address keep a local array alive?”

Can we return this array?

Move array creation into a function. Can its caller use the array?

int *make_values(void) {
    int values[4] = {0};
    return values;
}

// In the caller:
int *p = make_values();

During the call

values exists and contains four zeros.

After the return

values no longer exists. p is dangling, without any free.

Returning an address does not keep a local object alive.

Bridge from the repaired free example: “We now read before releasing the array. Suppose we move array creation into a helper function. Can we return a local array’s address?” Read the function without running an invalid access. Ask when values exists, then reveal During the call. Trace return values: the array expression supplies its first element’s address, not a copy of the array. Ask what ends when the call returns; reveal After the return. Say: “This is the same lifetime problem as before. Here leaving the function ends the array’s lifetime; no free is involved.” Reveal the takeaway. Do not promise a particular returned pointer value or printed result: GCC may warn and generate code that returns NULL. For this task, the caller can supply its own array, or the helper can allocate on the heap and the caller must later free it. The heap block survives the helper’s return even though its local pointer variable does not. Next compare these lifetimes explicitly. Memcheck is not a reliable detector for every automatic-storage lifetime error.

When does the storage end?

The pointer and the object it refers to have separate lifetimes.

Storage Lifetime ends
Ordinary local array When its block ends
Block from malloc When it is released with free
Global or static object When the program ends

Each recursive call has its own locals. Too many calls can exhaust the stack.

Use the two examples just seen: free ended the allocated array; return ended the helper’s local array. Point back to the stack/heap diagram, then read the table. A pointer being in scope is not proof that its target is alive. Globals/static objects have storage reserved before execution and remain for the program; ordinary locals have automatic storage duration. Recursive calls have separate locals: reveal the recursion sentence as a consequence, not a new topic. The heap block remains allocated even if a pointer goes out of scope or is overwritten. Bridge: “So changing the pointer does not release the block. What happens if we erase the only address before calling free?” Return to the repaired live-integers.c for the next experiment.

Does setting p to NULL free the block?

The block is still allocated. What if we erase its only address?

p = NULL;
free(p);

free(NULL) does nothing.

We lost the address: a memory leak.

Start from clean 05-integers.c; insert p = NULL before free. Fallback: demos/allocation/09-leak.c. Run make valgrind FILE=09-leak.c in demos/allocation with input 4 and locate definitely lost. Reveal the explanation and diagram. Connect to the lifetime comparison: a leak leaves the allocation alive but unreachable; a dangling pointer refers to an object that no longer exists. Repair by preserving p until free(p), then setting p = NULL only if useful. Edit that order and rerun. Repeated leaks consume more memory; process-exit cleanup does not repair a long-running program.

Who releases an unreachable block?

C: explicit responsibility

For every successful allocation, decide who will release it and when. Repeated leaks consume more memory.

Java: garbage collection

The runtime can reclaim unreachable objects automatically.

Start with the leak report still in mind: “We erased the only address. Will C find and reclaim that block for us?” Answer no, then contrast Java. Source slide 287 comparison. Garbage collection is not necessarily immediate and cannot reclaim reachable-but-unwanted objects. This is a short recap of responsibility, after students have observed a leak rather than before their first allocation.

Four functions in <stdlib.h>

We allocated, filled and released a block. We can also request zeros or resize it.

Function Purpose
malloc(bytes) Allocate uninitialised storage
calloc(count, size) Allocate storage with all bits zero
realloc(p, bytes) Resize an allocation; it may move
free(p) Release an allocation

Bridge: “Our program used malloc, a loop to write zeros, and free. The library also offers calloc for zeroed storage and realloc when a block must change size.” Summarize the API after the investigations and their repairs. Original overview only, not a new calloc/realloc lesson. For a nonzero request, realloc failure leaves the old block valid; assign through a temporary pointer. calloc sets all bits to zero, which is not a universal guarantee for pointer/floating representations.

The free contract

void free(void *pointer);   // Declared in <stdlib.h>
  • Pass the allocation’s start address, once.
  • free(NULL) does nothing; free returns no value.
  • An invalid or repeated release is undefined behaviour.

Bridge from the API table: “Before we use these blocks in larger structures, which addresses may we pass to free?” Ask about the malloc start address, p + 1, the local values array and NULL; then collect the formal details here. The repair slide deliberately carries only the edit and verification. An interior pointer, an automatic array address, or a previously freed address is not a valid argument.
