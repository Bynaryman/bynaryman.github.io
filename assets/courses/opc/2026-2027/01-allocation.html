Choose the capacity during execution

How can we reserve count integers?

int *p = malloc(count * sizeof(int));
if (p == NULL) {
    fputs("Allocation failed\n", stderr);

Count elements, request bytes

void *malloc(size_t size);   // From <stdlib.h>
int *p = malloc(100 * sizeof(int));
  • size_t is unsigned, with at least 16 value bits.
  • sizeof is an operator giving a size in bytes.
  • sizeof(int) is the size of one int, not the pointer.

Sizes depend on the platform. In C, the void * result needs no cast.

Inspect count * sizeof(int) in the program just run. Change input from 4 to 100; calculate the byte count on this machine. Preserve the generic count * sizeof(type) form. sizeof is an operator, not a function. size_t is unsigned and can represent at least 0 through 65535. No cast of malloc is required in C. For unrestricted external counts, check multiplication overflow before allocation.

2. Find and fix memory errors

The program prints a result. Is it correct?

It prints correctly. Is anything wrong?

Run the allocated version with 100, then inspect it:

make run FILE=03-missing-free.c
make valgrind FILE=03-missing-free.c

Where was the unreleased block allocated?

Run both commands in demos/allocation, entering 100 each time. First show normal output, then read the real Valgrind report. Find definitely lost, its allocation call site, and the heap summary. Do not display the solution first. The allocation remains unreleased when the local pointer goes out of scope. This is a leak even though output is correct and the process exits normally. The Makefile compiles with -g for source lines and -O0; Valgrind’s Memcheck checks this execution. Ask what action should happen after the last read. The next slide is the repair, shown after you add it in Vim.

Read first, then release

The array has been allocated and filled with zeros.

printf("first=%d, last=%d\n",

free(p);

free(p) releases the block after its last read.

All heap blocks freed

Valgrind now reports no leak.

Where does the program keep its data?

Illustrative 16-bit address space; real address widths and layouts vary.

Show the diagram after the missing-free repair. Locate the local count and pointer p in the active stack frame, and the allocated integer block on the heap. The pointer and its target are distinct objects. Calls grow the stack downward in this typical model; allocations occupy heap storage growing upward. Separate allocations need not be adjacent; real allocators may use other mappings. The layout is not a C guarantee.

What will the array contain?

malloc succeeded. We removed the loop that wrote zeros.

Write before reading

Restore the loop before printf.

for (int i = 0; i < count; ++i)
    p[i] = 0;

printf("first=%d, last=%d\n",

Every element now has a value before it is read.

Zero errors

Rerun Valgrind to check this execution.

Four integers: which write is outside?

count = 4. The allocation holds p[0] through p[3].

for (int i = 0; i <= count; ++i)
    p[i] = 0;

Invalid write

<= also allows i = 4. There is no element p[4] in this allocation.

Use i < count: four writes, with indices 0, 1, 2, 3.

Can we read after free?

p points to four integers initialised to zero.

free(p);

printf("first=%d, last=%d\n",
       p[0], p[count - 1]);

Invalid read

Valgrind points to printf: the block was already freed.

After free(p), p is a dangling pointer.

Start from clean 04-free.c and move free before printf. Ask whether the two reads are still valid. In demos/allocation run make valgrind FILE=07-dangling.c with input 4; fallback: demos/allocation/07-dangling.c. GCC can warn about the use after free; explain that warning too. Valgrind reports Invalid read of size 4 at printf and identifies both the previous free and the original malloc. The observed run may still print zeros, and it has no leak: neither fact makes the reads valid. Reveal the invalid read only after observing it. Then name the pointer state explicitly. The next slide explains that state and repairs the order.

Dangling pointer

A pointer to an object whose lifetime has ended.

free(p) releases the block; it does not set p to NULL.

Repair: finish reading before releasing the block.

printf("first=%d, last=%d\n", p[0], p[count - 1]);
free(p);

Distinguish the dangling pointer (state after the object’s lifetime ends) from the invalid read (using it to access that object). free does not remove the pointer variable or set it to NULL; the storage can be reused. The drawing is a lifetime model, not a claim about preserved byte values or a valid pointer value after free. Ask where free should go, then reveal the repair and edit it in Vim. Run make valgrind FILE=04-free.c with input 4 and read zero errors. Do not suggest setting p to NULL makes a subsequent read legal. Any other aliases would still be dangling. A second free is invalid too.

Does setting p to NULL free the block?

p is the only pointer to the allocated block.

p = NULL;
free(p);

free(NULL) does nothing.

We lost the address: a memory leak.

Start from clean 04-free.c; insert p = NULL before free. Fallback: demos/allocation/08-leak.c. Run make valgrind FILE=08-leak.c in demos/allocation with input 4 and locate definitely lost. Reveal the explanation and diagram. Contrast with the previous experiment: a leak leaves the allocation alive but unreachable; a dangling pointer refers to an object that no longer exists. Repair by preserving p until free(p), then setting p = NULL only if useful. Edit that order and rerun. Repeated leaks consume more memory; process-exit cleanup does not repair a long-running program.

Local objects can expire too

int *bad_result(void) {
    int value = 42;
    return &value;  // The local dies when this call ends.
}

A dangling pointer need not come from free

Returning an address does not extend an automatic object’s lifetime.

Tie this back to the stack frame in the opening diagram. Do not execute the invalid access. A function may instead return the value, fill caller-owned storage, or allocate a result with an agreed owner. Memcheck does not detect every stack lifetime error; the C lifetime rule is what matters here.

Who controls an object’s lifetime?

Static storage

Globals and static objects last for the whole program, with storage reserved before execution.

Automatic storage

Locals last for their block execution. Recursive calls have separate locals.

Storage is managed automatically. Deep recursion can exhaust the stack.

Compare three lifetimes only after the observed lifetime errors: globals/static objects last for the program; ordinary locals last for their block/call; the heap block lasts until free. Example 14 is optional supporting code for static versus automatic storage, not the lecture opening. Storage for static objects is prepared before execution. Recursive calls get distinct locals and can exhaust stack space; C implementations may also offer variable-length automatic arrays. Padding and layout affect frame storage, and separate heap allocations have no adjacency guarantee.

Who is responsible for reclamation?

C: explicit responsibility

For every successful allocation, decide who will release it and when. Repeated leaks consume more memory.

Java: garbage collection

The runtime can reclaim unreachable objects automatically.

Source slide 287 comparison. Garbage collection is not necessarily immediate and cannot reclaim reachable-but-unwanted objects. This is a short recap of responsibility, after students have observed a leak rather than before their first allocation.

Four functions in <stdlib.h>

Function Purpose
malloc(bytes) Allocate uninitialised storage
calloc(count, size) Allocate storage with all bits zero
realloc(p, bytes) Resize an allocation; it may move
free(p) Release an allocation

Summarize the API after the investigations and their repairs. Original overview only, not a new calloc/realloc lesson. For a nonzero request, realloc failure leaves the old block valid; assign through a temporary pointer. calloc sets all bits to zero, which is not a universal guarantee for pointer/floating representations.

The free contract

void free(void *pointer);   // Declared in <stdlib.h>
  • Pass the allocation’s start address, once.
  • free(NULL) does nothing; free returns no value.
  • An invalid or repeated release is undefined behaviour.

Collect the formal details here, after students have investigated leaks and dangling pointers. The repair slide deliberately carries only the edit and verification. An interior pointer, an automatic array address, or a previously freed address is not a valid argument.

Group data and access its members.

User-defined types

We want to keep a street name and a house number in one object.

Three tools

  • enum: name integer constants.
  • typedef: give a type another name.

Enumerations

enum day { mon, tue, wed, thu, fri, sat, sun };
enum day today;
today = wed;

By default, values start at 0 and increase by 1.

Named integer constants

mon is 0; wed is 2; sun is 6.

Generic syntax: enum tag { enumerators }; then enum tag variable. Preserve separate type definition, variable definition and assignment from source slide 302. Names can also have explicitly assigned integer values, but no additional exercise is needed.

A structure groups several members

struct address {
    char street[100];
    int number;
};

A type definition

Members may be integers, floating-point values, arrays, pointers or other structures. No address object exists yet.

Retain the source’s generic structure syntax and member-type list. Defining a type does not allocate an instance. A member declaration inside a C struct cannot have an object initializer; initialise a variable of that type instead.

Define a type, then create objects

struct address home;
struct address office;

These definitions allocate two distinct objects of the same type.

Local objects need initialisation

Ordinary local members have indeterminate values until initialised or assigned. The type definition alone sets no values.

Source slide 304 distinguishes type definition from variable definition and initialisation. Static objects would instead receive zero initialisation. Keep the automatic-local context explicit.

Initialising a structure

struct address home = { "Paul Bert", 12 };

Or combine the type and object definitions:

struct address {
    char street[100];
    int number;
} home = { "Paul Bert", 12 };

These are alternative forms, not declarations to place together in one scope. Initialisers follow member order; omitted members are zero-initialised. Allocation size includes any implementation-required padding, introduced next.

Same members, different order

struct grouped {
    int id1, id2;
    char c1, c2;
    float ratio;
};
struct interleaved {
    int id1; char c1;
    int id2; char c2;
    float ratio;
};

Restore both actual structure definitions from source slide 307, ahead of the byte diagram. Ask whether equal member types imply equal total size. The executable uses these same members/order, with descriptive type names.

Structure layout and alignment

Padding

The implementation may insert unused bytes between members and at the end to satisfy alignment requirements.

  • Members appear in declaration order.
  • sizeof(struct T) includes padding.
  • Layout and alignment depend on the implementation.

Preserve the source’s hardware motivation: alignment can simplify or speed memory access and may be required by the architecture. Correct its blanket claim that every processor always reads one word. No padding appears before the first member. Member alignment is type/platform dependent, not a universal single word size.

typedef: a name for a type

typedef int LENGTH;
typedef enum { FALSE, TRUE } BOOLEAN;
typedef struct date DATE;

Alias

A typedef introduces a type name, not an object or a distinct underlying type. Then write LENGTH width;.

Generic syntax in the original is typedef type IDENTIFIER; correct its LENGHT typo. BOOLEAN uses an anonymous enum: no enum tag is needed. DATE avoids repeatedly writing struct date (its definition appears next). This is C17; FALSE/TRUE are the original teaching example, not a replacement for the standard bool interface.
